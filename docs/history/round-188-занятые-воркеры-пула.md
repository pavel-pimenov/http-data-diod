# round 188 — реальная загрузка пула потоков: `l2_worker_active_workers` (P2)

## Что было не так

У пула потоков воркера были видны **глубина очереди** (`l2_worker_queue_size` ✓) и
**ёмкость** (`l2_worker_queue_capacity` ✓, раунд 169 ✓), но не было видно, **работают
ли воркеры** ✓. Глубина очереди в 0 означает и «всё выполнено» ✓, и «всё выполняется
прямо сейчас» ✓ — а это принципиально разные состояния ✓: в первом случае пул простаивает
✓, во втором — загружен ✓ (и именно во втором важно видеть, что воркеров не хватает ✓).

## Что сделано

- `ThreadPool` считает **занятых воркеров** ✓: атомарный счётчик ✓, который
  увеличивается на время выполнения батча и уменьшается после него ✓
  (`fetch_add`/`fetch_sub` ✓, `memory_order_relaxed` ✓ — счётчик сам по себе ✓).
  Аксессор `active_count()` ✓; `ThreadPoolWrapper` его прокидывает ✓ (для inline-режима
  `Type::NONE` — 0 ✓, там задача выполняется в вызывающем потоке ✓).
- Новая метрика `l2_worker_active_workers` (gauge ✓) в реестре воркера ✓;
  публикуется тем же тикером, что и глубина очереди ✓ (раз в ~5 с ✓).
- Дашборд L2-воркера: в панель очереди добавлена линия «занято воркеров» ✓.
- Каталоги README и `CATALOG` golden-check ✓ — итого **108** метрик в четырёх
  источниках ✓.

## Нюанс с батчами

Пул забирает задачи **батчами** (`g_dequeue_batch` ✓ — до 16 задач за раз ✓), поэтому
один воркер может выполнять несколько задач подряд ✓. Счётчик занятых воркеров
считает **воркеров** ✓, а не задачи ✓, — это и есть реальная загрузка пула ✓
(сколько воркеров занято) ✓.

## Тест

`ThreadPool: active_count follows the running tasks` ✓: пул на два воркера ✓, задачи
подставляются **по одной** ✓ (две задачи сразу забрал бы один воркер ✓ батчем ✓), и
проверяется, что занятых воркеров два ✓, а после завершения — ноль ✓.

Значение читается **до** проверок ✓, а гейты освобождаются до них же ✓: упавшее
утверждение не должно оставлять воркер заблокированным навсегда ✓ (иначе бинарь тестов
зависает ✓ — что и случилось при первой версии теста ✓).
