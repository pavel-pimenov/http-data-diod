# round 167 — потери спанов по причинам: `l2_tracing_spans_dropped_total{reason}` + исправление перепутанного счётчика

## Что было не так

`l2_tracing_spans_failed_total` — единственный счётчик потерь спанов на пути к
Jaeger — смешивал **разные** события:

- очередь спанов переполнилась (приложение создаёт спаны быстрее, чем экспортёр
  отправляет) — это проблема **потока**;
- отправка не удалась после всех попыток (экспортёр недоступен) — это проблема
  **экспортёра**;
- брейкер сбросил партию во время кулдауна;
- не успели на финальном сбросе при остановке.

По одному счётчику нельзя было отличить «экспортёр лежит» от «не успеваем
вывозить» — а это принципиально разные реакции (починить экспортёр vs. поднять
лимит очереди / сэмплировать реже).

## Побочная находка: перепутанный счётчик

Разбирая места инкремента, обнаружилось, что путь **Sentry**-брекера увеличивает
**Jaeger**-счётчик:

```cpp
// deliver_sentry_transactions(): батч к Jaeger уже доставлен, отбрасывается
// только Sentry-транзакция
if (cooldown_until != 0 && now_steady_ms < cooldown_until) {
  m_jaeger_metrics.m_spans_failed.Increment(batch.size());   // ← неверно
  if (m_sentry_metrics.m_spans_failed) {
    m_sentry_metrics.m_spans_failed->Increment(batch.size()); // ← верно
  }
  return;
}
```

То есть `l2_tracing_spans_failed_total` завышался на размер каждой сброшенной
Sentry-транзакции, хотя соответствующие спаны в Jaeger доставлены были. Инкремент
Jaeger-счётчика убран; Sentry-счётчик (счётчик транзакций) остался как был.

## Что сделано

- Новое семейство `l2_tracing_spans_dropped_total{reason}` в общем реестре
  `l2_common` (рядом с остальными метриками трассировки):

  | `reason` | Когда |
  |---|---|
  | `queue_full` | очередь спанов переполнена, спан отброшен при постановке |
  | `breaker_open` | партию сбросил брейкер Jaeger во время кулдауна |
  | `export_error` | отправка не удалась после всех попыток, партия потеряна |
  | `shutdown_flush` | финальный сброс при остановке не успел |

  Счётчик считает именно **потери** (а не неудачные попытки отправки), поэтому
  значение совпадает с числом потерянных спанов, а не с числом попыток.

- Список причин живёт в одном месте (`g_tracing_drop_reasons` в
  `src/tracing_metrics.hpp`): `AppContext` по нему предсоздаёт серию для каждой
  причины (prometheus-cpp отдаёт лейбл-семейство только после первого `Add()`, а
  в здоровом стеке потерь нет — без предсоздания семейства не было бы в
  `/metrics`), а логгер инкрементирует нужную.

- Семейство передаётся в логгер тем же общим типом `JaegerDeliveryMetrics`
  (раунд 162) — лишних параметров конструктора не появилось.

- Дашборд «Распределённая трассировка»: в панель спанов добавлен target
  `sum by (reason) (rate(l2_tracing_spans_dropped_total[1m]))` с легендой
  `{{reason}}` — по графику видно, чем именно теряются трассы.

- Каталог метрик в README (строка с меткой `reason` + абзац с расшифровкой
  причин), `CATALOG` в golden-check — итого **92** метрики в четырёх источниках.

## Тесты

- `AppContext: pre-creates the tracing span drop reason series` — проверяет, что в
  общем реестре есть все четыре причины (как в тестах предсоздания для
  воркерских и прокси-серий).
- Тест «jaeger breaker sheds batches while open» расширен: после того как
  брейкер сбросил партии, `dropped("breaker_open") > 0`, а `dropped("queue_full") == 0`
  — то есть потери различаются по причине, а не «всё в одну кучу».
