# Round 83: ускорение coverage-сборки (ccache + отключение PCH + объединённый gcovr)

## Мотивация

Каждый прогон `scripts/run-coverage.sh` на изменённых исходниках заново собирал
все 77 тестовых TU с `--coverage` (~112s), хотя ccache уже применён в builder-стадии.
Плюс тесты и gcovr — точки, которые тоже можно было ужать.

Стартовые замеры (Docker Desktop/colima, 4 vCPU):

| Этап | Было |
| --- | --- |
| coverage compile (77 TU, `--coverage`) | 112–121s |
| coverage unit tests (последовательно) | 88–92s |
| gcovr (3 прогона) | ~30s |
| export образа + `docker cp` | ~50s |

## Что сделано

1. **ccache для coverage.** В coverage-конфигурацию добавлены
   `-DCMAKE_C/CXX_COMPILER_LAUNCHER=ccache` и mount `/root/.ccache` (тот же, что у
   builder). Перед внедрением проверено на ccache 4.12.3: `gcc --coverage -c` под
   ccache даёт **hit** на повторной компиляции, и `.gcno` при этом
   **восстанавливается побайтово идентичным** — gcovr его принимает.
2. **Отключён PCH (`-DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON`).** Ключевая находка:
   компиляция с `-include .../cmake_pch.hxx` **не кэшируется ccache** — из-за этого
   доля cacheable-вызовов держалась на ~30%, и даже с прогретым кэшем coverage
   оставался на ~112s. Без PCH cacheable-вызовов стало **141/141 (100%)**.
   Результат: прогретая компиляция **112s → 6s** (70/70 hit), холодная — без
   заметной деградации (77 TU компилируются с нуля и раньше).
3. **Объединённый gcovr (HTML + JSON за один прогон).** Экономит второй проход.
   Нюанс gcovr 7.2: JSON-выход задаётся только как `--json=FILE`; форма
   `--json -o FILE` при двух запрошенных форматах молча скипается (в cov.json
   попадал HTML). Исправлено на `--json=/app/out/coverage/cov.json`.
4. **Тесты — оставлены последовательными.** Параллельный запуск двух бинарей
   замерен как wash (~85s против ~88s: `test_components` доминирует, оба упираются
   в общий CPU) и один раз дал просадку одной строки `http_client.cpp` в свежей
   сборке — пер-файловый гейт такое флагует. Детерминизм важнее.
5. `CACHE_BUST=1` в coverage-компиляции (как в builder): ручной способ форснуть
   полный пересбор без правки логики.

## Итоговые замеры

| Этап | До | После (прогретый ccache) |
| --- | --- | --- |
| coverage compile | 112–121s | **6s** |
| coverage unit tests | 88–92s | 88–92s (без изменений) |
| gcovr | ~30s | ~20s |
| повторный прогон без изменений | ~6 мин | **~2.5s** (layer cache) |

## Проверка

* `run-coverage.sh` зелёный: 555 кейсов / 2576 ассерций (`test_components`) +
  120 / 883 (`test_proxy_core`), гейты line 90 / branch 40 / production-branch 50;
* регресс-гейт пер-файловый: **OK** (допуск 0.0), production **6369/7113 = 89.54%**
  — совпадает с baseline (отключение PCH цифры не сдвинуло);
* clang-tidy не затронут (правка только Dockerfile).

## Замечание о флаках тестов

Отмечена периодическая нестабильность покрытия на сетевых тестах:
`http_client.cpp` L46 (валидация порта) и одна строка `nats_client.cpp`
иногда не набираются при разных прогонах одного и того же кода (наблюдалось и
последовательно, и параллельно). Это свойство тестов на таймингах, а не эффект
ccache: свежие прогоны стабильно дают 89.54–89.55%. Кандидат на отдельный раунд
(детерминизация сетевых юнит-тестов).
