# round 206 — автоматическая проверка прозрачности живой цепочки

## Что было не так

В round 203 прозрачность цепочки
`client → nginx:37015 → l2-proxy → NATS → l2-worker → ptokax:37014`
проверялась **разово, руками**: сравнивались ответы «напрямую в ptokax» и
«через цепочку» на plain text, бинаре, zlib-JSON, теле 1 MiB и
`/fly-test-port`. Результат в историю записан («ALL OK»), но повторить
проверку после очередного рестарта было нечем: команды жили в сессии, а не в
репозитории. При этом любое изменение на пути (новый флаг, base64-конверт,
заголовки, ретраи) могло незаметно сломать байтовую прозрачность — трафик
продолжал бы идти, но с искажёнными телами.

## Что сделано

Новый `scripts/live-chain-check.py` (stdlib, без зависимостей):

- **Сценарии** (по умолчанию 5): JSON `/fly-test-port`, plain text `/fly-stat`,
  zlib-сжатый JSON `/fly-stat`, бинарь с невалидным UTF-8 `/fly-zget`,
  тело 1 MiB `/fly-download`. `--skip-large` убирает последний.
- **Два пути**: цепочка запрашивается с хоста по `--chain-url`
  (по умолчанию `http://localhost:37015`), напрямую — `docker exec -i
  <container> curl ...` в контейнере сети хаба (по умолчанию `l2-worker` →
  `http://ptokax:37014`), тело передаётся через stdin.
- **Сравнение**: HTTP-статус, тело **побайтово** и `Content-Type` апстрима.
  Заголовки, которые добавляет nginx (`Cache-Control`, `traceparent`), не
  сравниваются — это не часть ответа хаба.
- **`X-Real-IP`**: `/fly-test-port` эхом возвращает IP вызывающего, поэтому
  прямой запрос обязан видеть тот же адрес, что и цепочка (nginx ставит
  `X-Real-IP: $remote_addr`). Значение не хардкодится под адрес Docker-сети,
  а определяется пробным запросом через цепочку — скрипт переносим между
  хостами.
- Ошибки транспорта (`docker exec` недоступен, curl rc≠0, нет разделителя
  заголовков) дают понятный FAIL, а не трейсбек; итог — таблица по
  сценариям и rc=1 при любом расхождении.

```bash
./scripts/live-chain-check.py                  # 5 сценариев
./scripts/live-chain-check.py --skip-large     # без 1 MiB
```

Скрипт намеренно **не входит в CI**: ему нужен живой режим
(`docker-compose.live.yml`), контейнер в сети `flylinkdc-hub_default` и
реальный PTOKAX, которых в CI-стенде нет.

## Проверка

- На живом стеке: `5/5 scenarios match byte-for-byte`, rc=0
  (статус/тело/`Content-Type` совпали на всех сценариях).
- Негативный тест: `--chain-url http://localhost:8888` (порт хаба вместо
  test-port) → `FAIL: chain probe returned HTTP 404`, rc=1.
- `python3 scripts/lint-python.py scripts/live-chain-check.py` — 0 замечаний;
  `shellcheck` — rc=0.

## Ограничения (честно)

- Проверка требует доступа к Docker и сети хаба — на машине без живого стека
  она неприменима; это ручной пост-деплойный чек, а не юнит-тест.
- Сравнивается `Content-Type`, но не полный набор заголовков: хаб может
  отдавать `Set-Cookie`/`Date`, которые заведомо различаются между вызовами.
- 1 MiB — не предел test-port (8 MiB); большие тела проверяются отдельно,
  если понадобится, потому что base64-конверт раздувает их на ~33 %.
