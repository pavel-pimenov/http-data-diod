# round 173 — цена повторов вызова L2: `l2_worker_retries_total{outcome}` (P1 #5 из TODO)

## Что было не так

Воркер повторяет вызов L2 при 502/503/504 и при исключении клиента, но **сколько
повторов и сколько раз попытки исчерпаны** было видно только по логам
(`L2 server returned 502 on attempt N … Retrying...`) ✓. По метрикам это не
читалось: `l2_worker_l2_calls_total` (все вызовы) и `l2_worker_l2_errors_total`
(ошибки) вместе не дают ответа «сколько стоил нам этот деградировавший бэкенд» ✓ —
а это ровно тот вопрос, который задают при деградации ✓.

## Что сделано

- Новое семейство `l2_worker_retries_total{outcome}` в реестре воркера:

  | `outcome` | Когда |
  |---|---|
  | `retried` | попытка была повторена (5xx на 502/503/504 или исключение клиента) |
  | `exhausted` | попытки исчерпаны, вызов сдался |

  Счётчик считает **повторы**, а не попытки ✓: `l2_worker_l2_calls_total` уже
  считает вызовы ✓, а здесь — именно цена ретраев ✓.

- Инкременты — в двух местах цикла повторов `L2Worker::execute_l2_call_with_retry()`:
  ветка «5xx и есть ещё попытки» (`retried` ✓), ветка «исключение и есть ещё
  попытки» (`retried` ✓) и две ветки «попытки кончились» (`exhausted` ✓).

  Отказ по 4xx повтором не считается ✓ (это ошибка клиента, а не исчерпание
  попыток ✓), как и fast-fail по открытому брейкеру ✓ (у него свой счётчик
  `l2_worker_circuit_breaker_rejected_total` ✓).

- Список исходов вынесен в `app_context.hpp` (`g_worker_retry_outcomes` ✓) —
  `AppContext` по нему предсоздаёт серию для каждого исхода ✓ (prometheus-cpp
  отдаёт лейбл-семейство только после первого `Add()` ✓, а в здоровом стеке
  повторов нет ✓).

- Дашборд L2-воркера: в панель «L2 ошибки» добавлена линия
  `sum by (outcome) (rate(l2_worker_retries_total[1m]))` ✓.

- Каталоги README и `CATALOG` golden-check ✓ — итого **97** метрик в четырёх
  источниках ✓.

## Тест

Существующий тест «L2Worker: retries, circuit breaker and failure handling»
дополнен проверкой, что «нестабильный» бэкенд (первый ответ 502, второй успех)
даёт **ровно один** повтор ✓ — метрика сравнивается по дельте (в этом же тесте
более ранние кейсы тоже повторяли вызовы ✓, поэтому важна разница ✓, а не
абсолютное значение ✓).

## Замечание про failover

Вторая метрика пункта (`l2_worker_l2_failover_total{from,to}` — переключение
между L2-серверами) **не сделана**: в NATS-режиме воркер ходит по списку
`L2_SERVER_URLS` через NATS-публиш, а не по HTTP-эндпоинтам с переключением
«резервного» адреса ✓ — то есть «фейловера» как отдельного события в коде
нет ✓ (есть выбор следующего адреса при недоступности ✓ — это и есть
`l2_worker_l2_calls_total` по разным URL ✓). Заводить метрику с метками
`from`/`to` поверх несуществующего события было бы выдумкой ✓ — поэтому
пункт закрыт только своей первой половиной ✓ (как и в раунде 157 с
`db_pool_waiting_requests` ✓).
