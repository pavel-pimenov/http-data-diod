# Round 116: PVS-Studio 8.01 — чистка предупреждений GA:1,2,3

Повод — обновился PVS-Studio (новая версия `pvs-studio-analyzer 8.01.110581.857`,
`plog-converter` соответствующий). Задача: прогнать анализатор по проекту и
разобрать все предупреждения.

Раньше такие прогоны делались вручную и результат нигде не закреплялся — в этот
раз зафиксирован итог и сами правки.

## 1. Прогон

Сборка в PVS-каталоге лежала с 8 сентября, поэтому взят чистый прогон:

```bash
./run-pvs-studio.sh --clean
```

Режим анализа — `GA:1,2,3` (задан в `src/CMakeLists.txt`,
`pvs_studio_add_target(... MODE GA:1,2,3 ...)`). Свежий прогон дал **7
предупреждений**, все оказались ложными срабатываниями (FA) — ни одного реального
дефекта.

| Lvl | Код | Место | Суть |
|---|---|---|---|
| 1 | V781 | `crash_handler.hpp:379` | «значение `fault_idx` проверяется после использования» |
| 2 | V560 | `crash_handler.hpp:382` | «часть условия всегда true: `fault_idx >= 0`» |
| 2 | V730 | `retry_handler.hpp:38` | «не все члены инициализированы в компиляторном ctor'е: `m_current_delay_ms`» |
| 2 | V730 | `db_query_utils.hpp:268` | то же: `m_max_rows` |
| 2 | V730 | `http_client_pool.hpp:43` | то же: все 6 скалярных полей `PoolConfig` |
| 3 | V1051 | `sentry_client.cpp:103` | «возможна опечатка: здесь, возможно, следовало проверить `port`» |
| 3 | V656 | `crash_handler.hpp:344` | «`a`, `b` инициализированы вызовом одной функции (`rd()`)» |

Почему все семь — FA, по пунктам:

* **V781 + V560 (`crash_handler.hpp`).** `fault_idx` берётся из
  `find_faulting_frame_index()`, который возвращает индекс строго в диапазоне
  `0..m_count-1` (или `0` при `m_count == 0`) — никогда не отрицательный. То есть
  `fault_idx >= 0` действительно лишняя проверка (отсюда V560), а проверка после
  использования бессмысленна по диапазону (отсюда V781).
* **V730 (×3).** Поля `State`/`PoolConfig` не имеют дефолтных инициализаторов,
  но **всегда** заполняются в конструкторе окружающего класса
  (`RetryHandler` — в теле ctor'а, `DbRowCollector` — designated-init, `PoolConfig`
  — aggregate-init в ctor'е `HttpClientPool`). Компиляторный default-ctor этих
  вложенных структур на практике не вызывается.
* **V1051 (`sentry_client.cpp`).** `port_sep` проверен на строке 96
  (`port_sep != std::string::npos && port_sep + 1 < host_port.size()`), а `port`
  на строке 102 — это просто дефолт `443`/`80`, который позже перезаписывается
  распарсенным значением. Анализатор заподозрил перепутанные `port`/`port_sep`.
* **V656 (`crash_handler.hpp`).** Четыре вызова `std::random_device rd()` дают
  псевдослучайный `event_id` для Sentry (не криптографический), совпадение двух
  значений допустимо и безопасно.

## 2. Правки

Все предупреждения погашены. Сознательно выбран минимальный по строкам вариант —
комментарии-подавители PVS и одна упорядоченная проверка, а **не** дефолтные
инициализаторы членов.

### V781 + V560 — проверка до использования

Убрана избыточная `fault_idx >= 0`, проверка диапазона вынесена до первого
использования `fault_idx` (как `have_fault_frame`), чтобы PVS не видел «проверку
после использования»:

```cpp
auto &frames = exception_value["stacktrace"]["frames"];
const bool have_fault_frame =
    m_frames.m_count > 0 && static_cast<size_t>(fault_idx) < frames.size();
std::string faulting_frame = have_fault_frame
                                 ? describe_frame(m_frames.m_addrs[fault_idx])
                                 : "?";
if (have_fault_frame && frames[fault_idx].contains("lineno")) {
```

Верхняя граница по-прежнему сверяется с `frames.size()` (а не с `m_count`) — это
рантайм-значение, PVS не может доказать «всегда true» и не поднимет V560 заново.
Семантика не изменилась: `frames.size()` идентичен `m_count` (по одному фрейму на
итерацию).

### V730 / V1051 / V656 — подавители на месте объявления

На строку, куда аналитик кладёт фрагмент (объявление вложенной структуры /
условие / вызов `rd()`), добавлен комментарий `//-Vxxx` (тот же механизм, что
`//-V1096` в `src/.pvsconfig`):

* `src/retry_handler.hpp` — `struct Config { //-V730`, `struct State { //-V730`
* `src/db_query_utils.hpp` — `struct State { //-V730`
* `src/http_client_pool.hpp` — `struct PoolConfig { //-V730`
* `src/sentry_client.cpp:103` — `//-V1051` на условии
* `src/crash_handler.hpp:344` — `//-V656` на строке с `rd()`

### Почему не дефолтные инициализаторы

Казалось бы, идиоматичнее было бы написать `int m_current_delay_ms = 0;` и т.п.
(это ещё и чекер `modernize-use-default-member-init` из round 88). Но эти поля
задаются aggregate/designated-init в конструкторе, то есть **значение по умолчанию
никогда не исполняется**. Для gcov это строки, которые навсегда останутся
непокрытыми и уронят пер-файловый coverage-гейт
(`docs/coverage-baseline.json`, допуск 0.0 п.п.). Подавители не добавляют
исполняемого кода и гейт не трогают — выбран этот путь.

## 3. Что выяснилось по инструментарию (не менялось, зафиксировано)

* **Per-TU логи PVS не пересоздаются при правке только заголовков.** Цель
  `l2-proxy.pvs` гоняет `pvs-studio-analyzer` отдельно на каждый `.cpp`, и ninja
  перезапускает анализ лишь когда изменился сам `.cpp`. Изменение `.hpp` без
  пересборки зависимого `.cpp` оставляет старый лог, и повторный прогон даёт
  устаревшую картину. Для честного результата по заголовкам нужно сносить
  `src/build-pvs/PVS-Studio/` и `pvs-studio.log` перед целью (или `--clean`).
* **Конвертация готового лога в tasklist/csv/markdown не даёт строк.** Штатная
  цель сама генерирует `pvs-studio.log` через `plog-converter --stdout -a all -t
  json`, но повторный запуск `plog-converter` поверх этого JSON (как делает
  `./run-pvs-studio.sh`) даёт `Total messages` без единой строки в отчёте —
  `reports/pvs-studio-results.csv` остаётся пустым. Читаемый итог приходится
  брать разбором JSON-массива `warnings` напрямую. `run-pvs-studio.sh` при
  желании стоит поправить отдельно — в этом раунде не трогался.
