# Round 195 — Ошибки валидации по отвергнутому полю: `l2_worker_request_validation_errors_total{field}`

## Что было не так

У воркера был счётчик отказов по валидации — `l2_worker_processing_validation_errors_total`,
— но **без разбивки по полю**: оператор видел «ошибки валидации растут» и не мог
ответить на главный вопрос — **что именно клиент присылает не так**. При этом
валидатор различает пять разных причин:

- обязательное поле отсутствует (`method` / `path` / `request_id`);
- метод не разрешён (`Method not allowed: DELETE`);
- путь длиннее лимита;
- путь не в списке разрешённых;
- тело больше лимита.

Все пять попадали в один счётчик, а различались только текстом в логе. Для
мониторинга это слепая зона: «клиенты шлют не тот метод» и «клиенты шлют
слишком большое тело» — это разные причины и разные действия (в первом случае
сверяют контракт клиента, во втором — лимиты).

Пункт P2 из `docs/TODO-metrika-kandidaty.md`:
`l2_worker_request_validation_errors_total` — «разбор ошибок валидации по полю;
риск — поле свободного текста, брать только enum-поле».

## Что сделано

### 1. Валидатор отдаёт имя отвергнутого поля

`RequestValidator::validate()` получил необязательный out-параметр
`std::string *failed_field`: при отказе туда попадает **имя поля из
конфигурации валидатора** (`method`, `path`, `body` либо имя обязательного
поля), а не текст причины.

Текст причины в метку не годится: он содержит клиентские значения
(`Method not allowed: DELETE`, `Path not allowed: /admin/secret`) — это
неограниченная кардинальность и потенциальная утечка клиентских данных в
`/metrics`. Имя поля берётся из закрытого набора самого валидатора, поэтому
кардинальность метки ограничена конфигурацией.

Текст ошибки в `error` при этом не изменился (ни одного символа) — он по-прежнему
уходит в лог и в тело ответа.

Добавлен `RequestValidator::required_fields()` — список обязательных полей из
конфигурации (нужен, чтобы предсоздать серии метрики).

### 2. Проводка

- `WorkerMetrics`: поле `m_request_validation_errors`
  (`prometheus::Family<prometheus::Counter>`) — **в конец структуры нельзя**:
  структуры метрик инициализируются позиционно, поэтому порядок объявления
  обязан совпадать с порядком регистрации (ровно как в раундах 182 и 186).
  Здесь порядок выровнен сразу, а новое семейство добавлено в тест контракта
  лейблов — перестановка была бы поймана;
- `init_worker_metrics()`: регистрация семейства + **предсоздание серий** по
  всем возможным полям (`method`, `path`, `body` + обязательные поля
  конфигурации). prometheus-cpp отдаёт помеченное семейство только после
  первого `Add()`, а здоровый воркер ничего не отвергает — без предсоздания
  семейства не было бы в `/metrics`;
- `L2Worker::parse_request_data()`: инкремент в серию отвергнутого поля рядом
  с уже существующим общим счётчиком валидации.

## Ограничения (честно)

- воркер отвергает запрос **до** обращения к L2, поэтому метрика показывает
  только «плохие входные данные», а не «плохие ответы L2»;
- поле `body` означает «тело больше лимита», а не «тело невалидно» — тело
  проверяется только по размеру;
- в `l2-server` этот счётчик не растёт: там другой обработчик (правило
  проекта — `l2-server` не развиваем).
