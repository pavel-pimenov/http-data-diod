# round 179 — гейт покрытия различает «потерю покрытия» и «сдвиг структуры»

## Симптом

Пер-файловый гейт покрытия (`scripts/coverage-regression-check.py`) падал, если
production-файл **понизил свой процент**. Но процент — не первичный признак: он
меняется и от того, что код **переехал в другой файл**.

Два реальных случая за сессию:

- **раунд 167**: суммирование серий помеченного семейства переехало из
  `stats_logger.cpp` в общий помощник в `metrics_manager.hpp`. Файл потерял четыре
  покрытые строки, знаменатель сократился, две прежние непокрытые строки остались —
  и процент просел на 0.08 п.п. Гейт упал, хотя потери покрытия не было: суммарно
  по трём затронутым файлам покрытие выросло (156/158 → 187/189).
- **раунд 174** (настоящая потеря): два новых счётчика NATS-клиента не
  выполнялись, потому что тесты не подключали метрики, — процент просел на
  0.24 п.п. Здесь гейт был прав ✓.

Оба случая выглядели одинаково — «просел процент», — и гейт не мог их различить.
Из-за первого случая CI был красным на заведомо зелёном коде (пришлось вручную
пере-анкорить baseline), и такой «ремонтный флейк» повторился бы при каждом
перемещении кода между файлами.

## Что сделано

Пер-файловая проверка теперь смотрит не на процент, а на **число непокрытых
строк в файле**:

| Событие | Признак | Реакция гейта |
|---|---|---|
| **регрессия** | непокрытых строк стало **больше** | падает (настоящая потеря покрытия) |
| **сдвиг** | процент просел, но непокрытых строк не прибавилось | печатается как `SHIFT`, **гейт не падает** |
| **новый файл** | production-файла нет в baseline | падает, только если в нём есть непокрытые строки; полностью покрытый — напоминание обновить baseline |
| **удалённый файл** | был в baseline, нет в отчёте | печатается, гейт не падает (это переименование/перенос) |

Ключевое: перенос кода уменьшает и покрытые, и непокрытые строки файла, но
**не увеличивает второе** — поэтому потеря и перенос теперь различимы.

Текст правила и его разбор добавлены в README (раздел про гейт покрытия ✓), а
опция `--max-drop` теперь управляет только порогом **отчёта** о сдвиге (сама
регрессия по непокрытым строкам допуском не регулируется ✓ — иначе гейт снова
стал бы «мягким» ✓).

## Проверка

- Синтетические случаи (проверены напрямую скриптом ✓):

  | Сценарий | Результат |
  |---|---|
  | `a.cpp` 95/100 → 93/100 (непокрытых 5 → 7) | `REGRESSION …, непокрытых строк стало больше на 2` → **rc=1** |
  | `a.cpp` 95/100 → 85/90 (перенос строк, непокрытых 5 → 5) | `SHIFT … — это перенос кода между файлами, а не потеря покрытия` → **rc=0** |
  | новый `c.cpp` 20/20 | `NEW …` + напоминание обновить baseline → **rc=0** |
  | новый `c.cpp` 15/20 | `NEW …` → **rc=1** |

- На реальных данных отчёта: просевший процент `trace_logger.cpp` (93.77% → 93.72%)
  теперь помечается как `SHIFT` ✓, а не как регрессия ✓.
- `scripts/lint-python.py` — 0 замечаний ✓; `python3 -m py_compile` — ок ✓.
- Гейт покрытия в CI на этом коммите — проверяется прогоном.
