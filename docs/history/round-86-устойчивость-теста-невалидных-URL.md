# Round 86: устойчивость теста невалидных URL (обе границы порта)

## Мотивация

В round 83–84 при анализе флак-строк выяснилось: `http_client.cpp:46`
(`throw "Invalid URL: port out of range"`) покрывалась ровно **одним**
вызовом (`count=1`) — единственный кейс `test_http_pipeline.cpp` с портом
`70000`. Строка с `count=1` хрупкая: любая потеря/слив одного счётчика
`.gcda` обнуляет её покрытие (именно это проявилось в откаченном параллельном
эксперименте round 83). Плюс: проверялась только верхняя граница
(`m_port > 65535`), а ветвь `m_port <= 0` не набиралась вовсе.

## Изменения

`src/test_http_pipeline.cpp`, тест «HttpClient: invalid URLs are rejected»:

* добавлен кейс `http://127.0.0.1:0/path` — покрывает нижнюю границу
  (`m_port <= 0`), ранее непокрытую ветвь условия на строке 45;
* добавлен кейс `http://127.0.0.1:65536/path` — вторая точка верхней границы,
  чтобы строка 46 набирала `count ≥ 2`.

`docs/coverage-baseline.json`: у `http_client.cpp` синхронизирован
`branches_covered` 79 → 80 (покрыта ветвь `m_port <= 0`); строки не менялись
(90/94) — гейт регрессии по строкам не затронут.

## Результат

| Метрика (http_client.cpp) | Было | Стало |
| --- | --- | --- |
| строка 46, `count` | 1 | **3** |

Строка 46 теперь набирается трижды и устойчива к единичной потере счётчика.
Общий production-итог не меняется (6372/7113 = 89.58%) — работа про
устойчивость, а не про прирост.
