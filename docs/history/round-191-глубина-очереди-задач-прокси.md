# Round 191 — Глубина очереди задач прокси: `l2_proxy_task_queue_size` + `l2_proxy_task_queue_capacity`

## Что было не так

У HTTP-пула прокси были три метрики: `l2_proxy_task_queue_enqueued_total`
(принято задач), `l2_proxy_task_queue_rejected_total` (отклонено) и
`l2_proxy_task_queue_wait_seconds` (сколько задача ждала воркер-тред). Не было
**глубины** — сколько задач стоит в очереди прямо сейчас.

Это был явно отложенный кусок пункта 9 из `docs/TODO-metrika-kandidaty.md`:
в раунде 169 закрыли ёмкость очереди пула потоков **воркера**
(`l2_worker_queue_capacity`), а прокси-часть была отложена с формулировкой
«у прокси очередь задач есть, но нет метрики глубины — ёмкость без числителя
бесполезна, поэтому сначала нужна `l2_proxy_task_queue_size`, и только потом
`l2_proxy_task_queue_capacity`».

Почему нельзя было просто «опросить очередь», как это сделано у воркера
(`l2_worker_queue_size` — фоновый тикер раз в ~5 с): у httplib список задач
приватный (`std::list<std::function<void()>> jobs_` внутри `ThreadPool`), наружу
отдаётся только `enqueue()`/`shutdown()`/`on_idle()`. Наружу торчит ещё и
`ThreadPool::queue_size()`? — нет: в вендоренной версии такого аксессора нет
вовсе (в проекте он есть только у собственного `ThreadPool` воркера). Единственное
место, которое видит и **приём** задачи, и **её старт**, — обёртка
`TimedTaskQueue` (`src/timed_task_queue.hpp`), которая и так уже измеряет
ожидание.

## Что сделано

### 1. Глубина считается в обёртке (не опросом)

`TimedTaskQueue` получил ещё два gauge'а:

- `l2_proxy_task_queue_size` — число задач, принятых пулом, но **ещё не
  забранных воркер-тредом**. Инкремент — в момент приёма (`enqueue()`),
  декремент — в момент старта задачи (внутри обёрнутой лямбды, до вызова
  самой задачи). Значит gauge считает именно *ждущие* задачи, а не
  выполняющиеся: «глубина 0» означает «никто не ждёт», а не «всё кончилось»;
- `l2_proxy_task_queue_capacity` — предел, который пул реально enforces.
  Ставится один раз при создании пула.

Отказ пула тоже корректно отражён: если `m_pool.enqueue()` вернул `false`
(очередь переполнена), инкремент глубины откатывается — отклонённая задача в
очереди не была.

Семантика глубины совпадает с тем, что ограничивает сам httplib: пул
отказывает, когда `jobs_.size() >= max_queued_requests_`, то есть когда
*ждущих* задач уже столько, сколько разрешено. Наш gauge декрементируется в
момент, когда воркер забирает задачу из списка, — то есть за миллисекунды до
того, как список уменьшится. Расхождение — одно окно, для мониторинга это
неразличимо.

### 2. Предел очереди стал настраиваемым

Ёмкость без числителя бесполезна, а числитель без ёмкости не позволяет
понять, «много» это или «норма». У прокси предела не было вовсе: httplib
создавался с `max_queued_requests = 0` (без предела), то есть очередь задач
росла вместе с нагрузкой — при перегрузке это неочевидный путь к росту
потребления памяти.

Добавлен конфиг `L2_PROXY_MAX_QUEUED_REQUESTS` (`src/config.hpp`:
`m_proxy.m_max_queued_requests`, по умолчанию **0 = без предела** — поведение
не меняется, пока переменную не задали явно). Валидация — неотрицательное
значение (`src/config.cpp`, `validate_threading_and_pool()`).

Что происходит при переполнении: httplib **не блокирует** и не отвечает 503,
а возвращает `false` из `enqueue()` → сервер закрывает сокет соединения
(`output_error_log(Error::ResourceExhaustion, …)` + `shutdown_socket`). То есть
клиент видит обрыв соединения, а не HTTP-ответ; это уже отражено в существующем
счётчике `l2_proxy_task_queue_rejected_total` и в справке README.

Нюанс, который легко пропустить: у httplib второй параметр `ThreadPool` —
это **максимум потоков**, а третий — предел очереди; при `max_n == 0`
максимум потоков равен базовому (`max_thread_count_ = max_n == 0 ? n : max_n`).
Мы передаём `max_thread_count = 0`, поэтому пул по-прежнему имеет 128 потоков
(`CPPHTTPLIB_THREAD_POOL_COUNT`), а новый ключ меняет **только** предел
очереди, но не число потоков.

### 3. Метрики, каталоги, дашборд

- регистрация — в реестре прокси (`init_proxy_metrics()`), рядом с
  существующими метриками очереди; порядок полей в `ProxyMetrics` совпадает с
  порядком регистрации (позиционная инициализация — ровно та ловушка, что
  разбиралась в раунде 182);
- `README.md`: обе метрики в таблице каталога прокси + пояснение в разделе
  «Насыщенность и доступность» (почему ёмкость 0 означает «без предела»);
- `scripts/metrics-golden-check.py`: обе метрики в `CATALOG`;
- `scripts/generate-grafana-dashboards.py`: новая панель 87 «Task queue depth
  (proxy)» — линии «depth» (`l2_proxy_task_queue_size`) и «capacity»
  (`l2_proxy_task_queue_capacity`); насыщение видно прямо на графике, а
  отношение глубины к ёмкости в PromQL не считается осознанно (при ёмкости 0
  это деление на ноль → NaN);
- `docker-compose.yml`: `L2_PROXY_MAX_QUEUED_REQUESTS` прокинут в сервис
  прокси (по правилам проекта — переменная, добавленная в C++, обязана быть в
  compose для сервисов, где используется);
- `docs/TODO-metrika-kandidaty.md`: пункт 9 переведён в «воркер (round 169) +
  прокси (round 191)», остаток — гистограмма ожидания в очереди **воркера**
  (воркер обрабатывает NATS-сообщения, а не HTTP-запросы, поэтому такая
  гистограмма ему не нужна — это отмечено явно, чтобы пункт не висел
  незакрытым).

### 4. Тесты

Оба теста `TimedTaskQueue` расширены:

- «counts accepted tasks and observes their wait»: после того как все задачи
  забраны, глубина 0, а ёмкость 0 (предел не задан — пул без него);
- «counts rejections when the queue is full»: предел 1 → ёмкость отражает
  ровно **1**; пока одна задача ждёт воркера, глубина 1 (отклонённая задача в
  очередь не попала); после освобождения гейта глубина снова 0.

## Ограничения (честно)

- Глубина — это счётчик **обёртки**, а не опрос внутреннего списка httplib:
  при аварийном завершении пула задачи, оставшиеся в списке, не стартуют и не
  декрементируют gauge (процесс в этот момент уходит, на метрики это
  не влияет, но «последнее значение» может быть ненулевым);
- предел очереди в httplib считается по *ожидающим* задачам, а не по общему
  числу соединений: при 128 занятых воркерах и пределе 1 в очереди может
  стоять 1 задача, а обслуживаться 129 соединений;
- сам предел (0 = без предела) выбран по умолчанию, чтобы не менять поведение
  стенда; включать его нужно осознанно (иначе переполнение очереди
  превращается в обрывы соединений вместо роста очереди).
