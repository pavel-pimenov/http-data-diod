# round 182 — перепутанные семейства метрик БД и пропущенные Python-тесты гейтов

## Симптом 1: метрика отдавала чужие метки

Новая метрика раунда 180 (`l2_worker_db_query_errors_total{error_class}` ✓) в живом
`/metrics` выглядела так:

```
l2_worker_db_query_errors_total{db="postgres",status="200",type="query"} 1
```

То есть имя семейства — правильное ✓, а набор меток — от **другого** семейства
(`l2_worker_db_requests_total` ✓). Причина: структуры метрик инициализируются
**позиционно** (aggregate initializer ✓), и порядок объявления полей в структуре
`WorkerMetrics` не совпал с порядком регистрации в `init_worker_metrics()` ✓ → два
однотипных семейства (`Family<Counter>` ✓) молча поменялись местами ✓.

Ни один гейт это не замечал ✓: golden-check сверяет **имена** семейств ✓ (а имя
было правильным ✓), и имя `l2_worker_db_query_errors_total` в списке тоже было ✓.
Поймал прогон, в котором посмотрели на метки глазами ✓.

Исправлено: порядок регистрации приведён в соответствие с порядком полей ✓;
добавлен тест-guard `AppContext: the DB error family is labeled by error class` ✓ —
он требует, чтобы у этого семейства был **ровно** один лейб `error_class` ✓, так что
подобный обмен местами больше не пройдёт незаметно ✓.

  случаи на новые правила ✓: «процент просел, но непокрытых строк не прибавилось →
  это сдвиг, а не регрессия» ✓, «новый файл с непокрытыми строками → гейт падает» ✓,
  «новый полностью покрытый файл → только напоминание» ✓.
- `tests/test_metrics_consistency.py` требует, чтобы набор «db»-семейств совпадал с
  условными ✓ → новое семейство `l2_worker_db_query_errors_total` добавлено и в

  набор теста ✓.
