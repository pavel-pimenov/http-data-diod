# Round 110: диагностика live-PG харнесса (guard по диску, видимая причина, libpq-проба)

Разбор round 109 показал, что первый прогон coverage-стадии упал не из-за кода:
**хост-диск был заполнен на 100%**, `initdb` не смог создать datadir, 12
live-DB-тестов ушли в SKIP, и гейт ветвей не добрал ~1.2 п.п. Самое неприятное —
харнесс об этом молчал: в логе не было ни строки, объясняющей скип. Этот раунд
чинит именно диагностику: тест-инфраструктура, не продакшн-код.

## 1. Почему скип был невидимым

Два почти одинаковых эфемерных Postgres-харнесса, оба «немые» на отказе:

* `src/test_db_live.cpp` (`PgServer`): часть путей падения логировалась на
  уровне warn, но у `ensure_started()` есть тихий ранний выход
  `if (m_failed) return false;`, а свободное место нигде не проверялось —
  `initdb` падал, и тест просто скипался;
* `src/test_nats_live.cpp` (`pgtest::PgSrv`, строки ~1412+): **все** пути
  падения — `if (m_bindir.empty()) return false;`, `if (!t.m_ok) return false;`,
  `mkdtemp`/`chown`/`run_wait`/`pg_wait` — возвращали `false` без единой
  записи в лог.

То есть окружение говорило «кластер не поднялся», а тест — «нет Postgres в
этом окружении», и связать одно с другим можно было только вручную.

## 2. `src/test_pg_diag.hpp` — общая диагностика для обоих харнессов

Новый тестовый заголовок (в сборку попадает только через include, в CMake
ничего добавлять не нужно):

* `free_bytes(path)` — `statvfs`;
* `enough_free_space(path = "/tmp")` — порог **256 МиБ**: если места меньше,
  кластер вообще не поднимается, а причина пишется в лог
  (`only N MiB free on /tmp (need 256 MiB) - cannot start a postgres cluster`);
* `fail(reason)` — причина пишется **дважды**: через `Logger::error` и напрямую
  в `stderr`. Второй канал принципиален: spdlog пишет ещё и в файл, а sink
  может отказать ровно в том сценарии, который надо объяснить (диск полон);
* `log_tail(path, 600)` — хвост `initdb`/серверного лога с плющеными переводами
  строк, чтобы «сервер не поднялся» превращалось в конкретную ошибку Postgres
  (`no space left on device`, `could not create shared memory`, ...).

## 3. `test_db_live.cpp` — guard + причины

* перед `reserve_loopback_port()` добавлен `enough_free_space()`;
* все отказы теперь докладываются: `mkdtemp`/`chown`/`fork` — с `strerror(errno)`,
  падение `initdb` — с кодом возврата и хвостом лога, таймаут готовности — с
  хвостом серверного лога.

## 4. `test_nats_live.cpp` — guard, причины и libpq-проба

Тот же guard и те же доклады в `pgtest::PgSrv::start()`, плюс исправлена проба
готовности: **`pg_tcp_probe` → `pg_sql_probe`**.

Голый TCP-accept означает лишь, что postmaster занял порт; сразу после старта SQL
соединения ещё получают «the database system is starting up». В `test_db_live.cpp`
ровно эту пробу заменили в round 107, но дублирующий харнесс остался на старой —
то есть воркер мог стартовать раньше, чем кластер начнёт принимать SQL. Теперь
оба харнесса ждут именно принятой SQL-сессии (`libpq-fe.h` в этом TU уже
подключён).

## 5. Что осознанно не делалось

* харнессы **не** объединены в один: `PgServer` и `pgtest::PgSrv` по-прежнему
  дублируются (различаются владельцем datadir/логом/пробой). Полная выемка —
  отдельная задача, здесь она была бы самым рискованным изменением тестов;
* failure-ветви новой диагностики в покрытие не попадают: они исполняются
  только в сломанном окружении, а тестовые файлы и так вне baseline.
