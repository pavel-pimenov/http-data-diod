# Round 111: покрытие достижимых error-ветвей Postgres, детектора дублей и Jaeger-recovery

Продолжение линии покрытия (round 109): берём только **реально достижимые** блоки,
которым не нужен новый брокер и новая инфраструктура. Разбор оставшихся
«непокрытых строк» подтвердил, что большая их часть — артефакты gcov (первая
строка многострочного `Logger::*`/`std::format(...)` отчётится нулём, хотя блок
исполняется) или мёртвые защитные ветви; здесь выбраны те, что действительно
проталкиваются из тестов.

## 1. `duplicate_detector.cpp` — тай-брейк эвикции (+2 строки)

`evict_lowest_count_locked()` сравнивает записи по `m_count`, а при равных
счётчиках — по `m_first_seen_ms` (строки 195/197). Вторая ветка компаратора
никогда не исполнялась: во всех тестах эвикция шла над набором, где счётчики
различались, либо сравнивать было нечего.

Новый `[duplicate-detector]`-тест держит в кэше **две записи с одинаковым
`m_count == 1`** (`m_max_entries = 2`, три разных тела; третья запись запускает
эвикцию с двумя равными записями). Контейнер `m_entries` — `std::unordered_map`,
поэтому при равных счётчиках жертва зависит от порядка бакетов и от совпадения
`m_first_seen_ms` в одну миллисекунду; тест не привязывается к конкретной жертве,
а проверяет инвариант: ровно одно из двух равных тел выжило
(`first_tracked != second_tracked`).

## 2. `duplicate_detector.cpp` — LRU per-client (+1 строка)

В `evict_oldest_client_locked()` (178-190) компаратор по `m_last_seen_ms`
(строка 183) тоже не исполнялся — существующие тесты держали в per-client мапе
одну запись. Новый тест с `m_per_client_max_entries = 2` заводит двух клиентов
и третьим вызывает эвикцию при двух записях: компаратор исполняется, размер
мапы остаётся на границе.

## 3. `db_query_executor_postgres.cpp` — «нулевой» result set (+3 строки)

`execute_query()` отдельно обрабатывает `PQnfields(res) == 0` («Statement
returned no result set», 255-257). PostgreSQL допускает таблицу без колонок, и
`SELECT * FROM t` по ней возвращает `PGRES_TUPLES_OK` с нулём полей — ровно этот
случай не был покрыт. Новый `[db-live]`-тест создаёт `CREATE TABLE pg_zero_col ()`
через raw-libpq helper и проверяет 422 с этим текстом.

## 4. `db_query_executor_postgres.cpp` — убитый backend в `ping()` (+3 строки)

`ping()` сначала ставит `statement_timeout`, и отказ этого шага — отдельная ветвь
(302-306), которая не исполнялась: во всех тестах соединение либо живое, либо
полностью пересоздаётся. Новый `[db-live]`-тест с `pool_max=1` делает успешный
запрос (соединение уходит в idle), затем вторым raw-коннектом убивает бэкенд пула
(`pg_terminate_backend`) и вызывает `ping()`: локальный объект соединения жив, но
`SET statement_timeout` падает → ветвь срабатывает. Второй `ping()` проверяет, что
пул выбросил мёртвое соединение (`PQstatus` стал `CONNECTION_BAD` → `PQfinish` +
`--m_total`) и восстановился на новом.

Строка 303 остаётся с `count=0` — это артефакт gcov (первая строка многострочного
`Logger::warn`), исполнение подтверждают покрытые продолжения 304-306.

## 5. `trace_logger.cpp` — «Jaeger send recovered» (+1 строка)

Ветка «доставка восстановилась после отказа» (`m_consecutive_failures > 0` в
успешном `send_batch`, 722-725) не исполнялась: нужна неудачная попытка **и**
успешная в одном логгере.

Первая (очевидная) идея — битый endpoint, затем сервер на том же порту — упирается
в учёт пула: при исключении внутри `send_batch` соединение не возвращается в
`HttpClientPool` (единственный вызов `release_connection` стоит на успешном пути,
строка 720), поэтому один упавший батч (1 попытка + 3 ретрая = 4 соединения) при
`max_size=3` исчерпывает пул навсегда, и успешной отправки после серии падений уже
не будет. Поэтому тест падает **ровно один раз**: у мок-сервера
`TraceMockServer` появился режим `hang_requests` — первый POST «зависает» дольше
read-таймаута клиента (2 c), первая попытка честно падает, а повтор из того же
flush-цикла сразу получает 200. `hung_count()` подтверждает неудачу, `body_count()`
— доставку, то есть восстановление прошло с ненулевым счётчиком отказов.

Строка 723 снова остаётся `count=0` как артефакт первой строки `Logger::debug` —
исполнение подтверждает покрытая строка 724.

## 6. `sentry_client.cpp` — fallback уровня (+1 строка)

`level_to_string()` заканчивается `return "error";` (147) после `switch` по всем
значениям `EventLevel` — ветка достижима только вне-диапазонным значением. В
существующий тест «every level maps to its Sentry string» добавлена проверка
`level(static_cast<sentry::EventLevel>(99)) == "error"`.

## Обнаруженный дефект (осознанно не правился здесь)

`HttpClientPool`: слот `m_total_clients` не возвращается, если потребитель
(`send_batch` → `post_no_response`) бросил исключение — `release_connection()`
вызывается только на успешном пути. Практическое следствие: одна серия отказов
Jaeger (4 попытки при `max_size=3`) навсегда вычерпывает пул трассировки, и
«breaker» перестаёт быть восстановимым. Это продакшн-поведение, поэтому в раунде
покрытия не менялось — кандидат в отдельный раунд (нужны свои тесты + прогон
live-сценария).
