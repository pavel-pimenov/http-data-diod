# round 180 — ошибки запросов БД по классу SQLSTATE: `l2_worker_db_query_errors_total{error_class}` (P2)

## Что было не так

У слоя БД не было **ни одной** метрики ошибок ✓: неудачный запрос уходил в ответ
(`SQL_ERROR`, 422) и в лог ✓, а по метрикам было видно только, что запросы идут
(`l2_worker_db_requests_total{db,type,status}` ✓) ✓. Но «запросы идут» и «запросы
падают» — разные вещи ✓, а *почему* падают — самое интересное:

- класс `08` — проблема с соединением (БД недоступна/переподключается ✓);
- класс `42` — ошибка синтаксиса в SQL клиента ✓;
- класс `23` — нарушение ограничения целостности ✓;
- класс `53`/`55`/`57`/`58` — нехватка ресурсов, объект не в нужном состоянии,
  вмешательство оператора, системная ошибка ✓.

Без разбора по классу все ошибки БД выглядели одинаково ✓ — «DB Gateway 422» ✓.

## Что сделано

- Новое семейство `l2_worker_db_query_errors_total{error_class}` в реестре воркера ✓.
  Метка — **класс SQLSTATE** (первые два символа пятисимвольного кода ✓), а не полный
  код и не текст сообщения ✓: полный код — строка на каждую БД (неограниченная
  кардинальность ✓), текст сообщения — тем более ✓. Класс — короткая ограниченная
  метка ✓.

- Проводка построена по уже готовой схеме слоя БД ✓ (`set_pool_metrics` ✓,
  `set_pool_saturation_metrics` ✓):
  - `DbQueryExecutor` получил виртуальный `set_error_metrics()` ✓ (драйверы, которые
    не умеют сообщать класс — Oracle ✓ — наследуют реализацию базы и просто не
    публикуют ✓);
  - `DbExecutorBase` хранит указатель на семейство и считает ошибку через
    `count_query_error()` ✓ (счётчик `nullptr` → вызов безопасно ничего не делает ✓ —
    драйвер может быть «проводён» позже первого отказа ✓);
  - `DbQueryHandler` прокидывает семейство в каждый исполнитель ✓ при инициализации ✓;
  - воркер (`l2_worker_nats.cpp`) связывает семейство из своих метрик ✓.

- PostgreSQL-исполнитель извлекает SQLSTATE из результата
  (`PQresultErrorField(res, PG_DIAG_SQLSTATE)` ✓) и берёт из него первые два символа ✓;
  если кода нет — метка `unknown` ✓.

- Классы, которые PostgreSQL возвращает на практике, **предсоздаются** при старте ✓
  (список в `db_query_utils.hpp` ✓ — `g_db_error_classes` ✓): `08`, `22`, `23`, `25`,
  `42`, `53`, `55`, `57`, `58`, `72`, `F0`, `HV`, `P0`, `XX`, `unknown` ✓. Иначе
  семейство не попало бы в `/metrics` до первого отказа ✓ (а гейт требует, чтобы
  семейство присутствовало ✓). Класс вне списка появится при первом использовании ✓.

- Дашборд L2-воркера: в панель запросов БД добавлена линия
  `sum by (error_class) (rate(l2_worker_db_query_errors_total[1m]))` ✓.
- Каталоги README и `CATALOG` golden-check ✓ — итого **103** метрики в четырёх
  источниках ✓.

## Имя метрики

В TODO она была названа `l2_worker_db_query_errors_total` ✓ — так и сделано ✓:
исполнитель запросов работает в воркере ✓ (прокси лишь проксирует DB-Gateway в
NATS ✓), поэтому метрика в реестре воркера ✓.

## Тест

`DbExecutorBase: query errors are counted by class` ✓: без привязанного семейства
вызов безопасен ✓; после привязки ошибка класса `42` и класса `23` считаются в свои
серии ✓, а отсутствующий класс даёт ноль ✓.
