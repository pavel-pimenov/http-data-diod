# round 158 — CI: гонка двух писателей в gauge глубины очереди трейсинга

## Симптом

CI-прогон `39143753827` (коммит `6169f98`, раунды 156-догон + 157): три джоба
зелёные — `Build + unit tests + NATS smoke` (**впервые зелёный**: подмена
`GRAFANA_URL` убрана в раунде 156, `| head -30` — в догоне 156), `Coverage gate`
на `ubuntu-24.04-arm`, `clang-tidy (full sweep)`, — а `cppcheck (full sweep)`
красный. Причём упал он не на cppcheck: этот джоб сначала собирает образ (а
сборка образа прогоняет юнит-тесты), и на шаге тестов получил `exit code 42`.

Детали из лога:

```
test cases:  592 |  591 passed | 1 failed
assertions: 2837 | 2836 passed | 1 failed
/app/test_trace_logger.cpp:362: FAILED:
  REQUIRE( wait_for_condition([&] { return env.queued() == 0.0; }, 2000) )
```

тот же самый `exit code 42` я до этого поймал локально в стадии `coverage`
(повторный прогон тогда прошёл — «флейк»).

## Корень

`l2_tracing_queue_size` (gauge глубины очереди спанов) пишут **два места**:

- `JaegerLogger::enqueue_span()` — после `push()` кладёт в метрику
  `PushOutcome::m_size`, то есть глубину очереди сразу после добавления;
- `JaegerLogger::sender_loop()` — сразу после `wait_and_take()` кладёт
  `m_span_queue.size()`, то есть глубину очереди **без только что взятого батча**.

Оба значения выводятся из одного и того же счётчика, но записи в gauge никак не
упорядочены. Гонка:

1. поток теста: `push()` → очередь `1` → `notify_one` → **собирается** записать `1`;
2. поток отправителя (уже ждал на mutex) просыпается раньше и забирает элемент →
   очередь `0` → пишет `0`;
3. поток теста дописывает `1` **после** — gauge остаётся `1`.

Дальше очередь пуста, `wait_and_take()` возвращает `Idle` и больше **никогда** не
переписывает gauge — значит `1` висит до следующего `take()`, которого не будет.
Поток отправителя при этом бросает батч, `l2_tracing_spans_failed_total`
инкрементируется, `queued()` навсегда остаётся `1`, и ожидание «очередь пуста»
истекает.

Лог CI это подтверждает: в 27.54 батч уже отброшен (`Jaeger batch send failed
after 3 retries, dropped 1 spans`), дальше до 29.60 — **ни одной** строки от
логгера (отправитель спит в `wait_and_take`), а ожидание всё ещё видит ненулевой
gauge.

Это не только флейк теста: в проде то же самое означает «очередь трассировки
глубины 1 на пустом сервисе», причём значение не исправляется, пока не придёт
следующий спан.

## Почему гонка вообще возможна так часто

Поток теста после `push()` возвращается, вычисляет аргумент и делает store; поток
отправителя уже стоял на mutex в `wait_for` и после `push()` получает его
немедленно — то есть берёт элемент и пишет `0` примерно в те же микросекунды.
Кто из двух store'ов окажется последним — фактически монетка. На медленном
2-vCPU-CI исход «не повезло» и выпадал; локально тоже выпадал один раз из двух
прогонов покрытия.

## Что сделано

`sender_loop()` перепубликует глубину **после** `mark_processed()`, то есть после
полной обработки батча: последний писатель — потребитель, и значение сходится к
истинной глубине очереди. Интервал между store'ами теперь не микросекунды, а
длительность отправки (миллисекунды и больше: у мёртвого Jaeger это три попытки
с паузами 100/200 мс), поэтому «невезучий» порядок требует паузы планировщика
>300 мс между возвратом `push()` и его store.

Почему не убрали store из `enqueue_span()`: на нём держится поведение «сразу
видно глубину после налива» — в том числе тест `queued() == 10000` (полная
очередь) и видимость переполнения при `DropOldest`.

Почему не «один писатель через колбэк в `AsyncSenderQueue` под его mutex»: это
правильнее по строгости, но это шаблонный интерфейс + `std::function` в горячем
пути + свои юнит-тесты очереди; выигрыш против двух store'ов, разнесённых на всю
длительность отправки, — только теоретический (нужен полный провал планировщика
внутри одного теста).
