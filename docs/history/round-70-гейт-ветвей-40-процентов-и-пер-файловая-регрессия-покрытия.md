# Round 70: гейт ветвей 40% + пер-файловый гейт регрессии покрытия

## Мотивация

Round 69 поднял построчное покрытие до 90.3% и включил `--fail-under-line 90`, но:

- **ветвевое покрытие осталось без контроля** — 40.6% по проекту (47.0% без
  тестовых TU) лежало в README как чисто информационная цифра: можно было потерять
  ветви, не тронув ни одной покрытой строки (рефактор `if` → ранний `return` меняет
  ветви, а строки оставляет покрытыми);
- **глобальный гейт не защищает от локальной регрессии**: добавил непокрытые строки
  в один файл, но компенсировал тестами в другом — общая доля держится, а конкретный
  файл деградирует. Такая деградация накапливается годами и остаётся незамеченной.

Раунд ставит обе защиты: гейт по ветвям и пер-файловый гейт регрессии.

## Изменения

### 1. `src/Dockerfile` — второй гейт и JSON-отчёт

В coverage-стадии к `--fail-under-line 90` добавлен `--fail-under-branch 40`:
gcovr OR-ит коды своих гейтов (2 — строки, 4 — ветви), поэтому ненулевой выход
валит сборку образа независимо от того, какой из двух порогов нарушен. Порог 40
взят с запасом ~0.6 п.п. к измеренным 40.6%.

Тем же RUN'ом рисуется второй отчёт — `cov.json` (`gcovr --json`, те же
`--filter`/`--exclude`, без гейтов) в `/app/out/coverage/`. Он нужен
пер-файловому гейту: HTML для людей, JSON для скрипта.

Проверка семантики гейтов (в контейнере `http-data-diod:coverage`):
`оба порога пройдены → 0`, `--fail-under-branch 41 → 4`, `--fail-under-line 91 → 2`.

### 2. `scripts/coverage-regression-check.py` (новый) — пер-файловый гейт

stdlib-only скрипт в стиле остальных `scripts/*.py`:

- читает отчёт gcovr `--json`, считает по каждому файлу покрытые строки
  (некодовые строки `gcovr/noncode` исключаются) и для baseline — ветви;
- сравнивает с закоммиченным `docs/coverage-baseline.json` и **падает** (rc=1),
  если production-файл понизил свой процент покрытия (по умолчанию допуск 0 п.п.,
  `--max-drop <п.п.>` расширяет его);
- падает и на **новый production-файл**, которого нет в baseline, — так baseline
  обновляется только осознанно, вместе с кодом;
- удалённые из отчёта файлы печатает как `REMOVED` (сам по себе exit 0) — сигнал
  обновить baseline;
- **тестовые TU (`test_*.cpp`) не сравниваются и в baseline не пишутся**: их
  качество контролируют глобальные гейты строк/ветвей, а их локальные просадки
  (недостижимые в тесте ветки) не являются регрессией продакшена;
- `--update` переписывает baseline из текущего отчёта.

Exit codes: 0 — ок, 1 — регрессия/новый файл/пустой baseline, 2 — не удалось
прочитать отчёт или baseline.

### 3. `scripts/run-coverage.sh` — запуск гейта

После извлечения отчёта из образа скрипт вызывает
`coverage-regression-check.py --report $OUT_DIR/cov.json`. Из-за `set -euo pipefail`
регрессия валит весь `run-coverage.sh`, то есть job `coverage` в CI. Первый запуск
(до создания baseline) ожидаемо падает с «baseline пуст или не найден — запусти
--update»: так гейт не бывает молча выключенным.

### 4. `docs/coverage-baseline.json` (новый) — база для сравнения

Сгенерирован из свежего отчёта: 76 production-файлов, 5689/7018 строк (81.06%).
Каждая запись хранит `lines`, `covered`, `branches`, `branches_covered` — ветви в
baseline пишутся как снимок для наблюдаемости, сравниваются пока только строки.
Файл обновляется командой `scripts/coverage-regression-check.py --update` и
коммитится в том же PR, что и код.

### 5. `tests/test_coverage_regression.py` (новый) — 10 unit-тестов

Без docker и сети: отчёты gcovr собираются из строк во временных файлах.
Покрыто: подсчёт строк/ветвей с `gcovr/noncode`, детект регрессии, допуск
`--max-drop`, новый и удалённый файл, игнорирование `test_*.cpp`, roundtrip
baseline, сценарии `main()` (update → ок → регрессия → rc=1, отсутствие baseline,
несуществующий отчёт → rc=2).

### 6. Документация и CI

- `README.md`, раздел «Покрытие юнит-тестов»: таблица гейтов (строки 90% /
  ветви 40% / пер-файловая регрессия) с текущими цифрами, команды запуска
  regression-скрипта, актуальные цифры branch-покрытия (40.6% всего, 47.0% без
  тестовых TU — старые «~41%/~53%» устарели), обновлён итог в таблице
  «Текущие цифры» (было «~97.4%», что считалось по старому знаменателю);
  перечислены слабейшие production-файлы по ветвям;
- `.github/workflows/ci.yml`: имя job `coverage` и название шага теперь про
  оба порога и про регрессию.

## Проверки

- `./scripts/run-coverage.sh` — **rc=0**: сборка образа проходит оба порога
  gcovr, затем `OK: регрессий покрытия нет`;
- негативный прогон гейтов в контейнере: `--fail-under-branch 41 → 4`,
  `--fail-under-line 91 → 2` (пороги реально падают, а не только печатают);
- `python3 -m unittest discover -s tests` — 94 теста (10 новых по regression-скрипту);
- `python3 scripts/lint-python.py` — 0 проблем;
- `./scripts/ci-gate.sh all` — rc=0;
- `./scripts/pre-commit.sh` (unit + offline + runtime + shellcheck + clang-tidy).

## Как дальше

- поднимать порог ветвей по мере роста (40 → 45 → 50): главное резерв —
  production-файлы с живыми зависимостями (DB/брокер);
- при добавлении нового production-файла CI намеренно падает до `--update`
  baseline — это фича, а не баг: baseline обязан обновляться в том же PR.
