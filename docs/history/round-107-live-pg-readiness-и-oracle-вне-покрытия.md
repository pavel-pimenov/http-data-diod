# Round 107: устойчивость live-Postgres харнесса, Oracle вне покрытия, переанкор baseline

## 1. Флейк live-Postgres в юнит-тестах (`src/test_db_live.cpp`)

Симптом: `./rebuild-and-run.sh` и `./scripts/run-coverage.sh` периодически падали
на шаге юнит-тестов — 2…4 кейса `[db-live]` (`REQUIRE(ex.init())`,
`REQUIRE(PQstatus(m_conn) == CONNECTION_OK)`, `REQUIRE(handler.init(...))`)
с «failed to connect to 127.0.0.1:<port>». Повторный прогон обычно проходил.

Диагностика по логу прогона: падали **первые** live-тесты, а **более поздние на
том же сервере** проходили (упал `DbQueryHandler: routes live postgres query and
ping` (676), а `re-init`/`partial init`/`empty db` (729/752/802) прошли). Значит
сервер не «умирал» — он ещё не начинал принимать SQL в момент, когда харнесс
объявлял его готовым.

Причина: готовность определялась `tcp_probe()` — голым TCP-accept. Postmaster
открывает TCP-порт раньше, чем кластер начинает обслуживать сессии, и на
подключение в этот момент отвечает «the database system is starting up»
(`PQstatus == CONNECTION_BAD`). Первые тесты попадали в это окно.

Фикс:

* `tcp_probe(port)` → `sql_probe(port)`: проба делает полноценную libpq-попытку
  (`PQconnectdb` с `connect_timeout=1`, `dbname=postgres user=postgres`) и
  считает сервер готовым только при `PQstatus == CONNECTION_OK`; `start()` ждёт
  эту пробу (`wait_for_condition`, тот же 10-секундный дедлайн);
* `ensure_started()` проверяет не только `m_pid > 0`, но и `alive()`: если процесс
  всё же умер (крах/OOM/внешний kill), datadir с устаревшим портом сбрасывается и
  кластер поднимается заново, а не отдаётся «мёртвый» сервер;
* `stop()` дополнительно чистит datadir (`cleanup_datadir()`), а не оставляет
  `/tmp/pgdb-*` после сценария «connection lost mid-pool»;
* удалён ставший ненужным `#include <cstdint>`.

## 2а. Почему у «слабых» файлов непокрытые строки — это потолок измерения

Проверены непокрытые строки целевых файлов (round 107 задумывался как
покрытийный). Оказалось, что подавляющее большинство из них — артефакты
атрибуции gcov, а не пробелы в тестах:

* первые строки многострочных `Logger::{debug,info,warn}` — gcov ставит счётчик
  на строку с аргументами/закрывающей скобкой, а первая строка вызова остаётся
  `count=0` навсегда. Пример (`http_client_pool.cpp`): строка 26 `count=0`, а
  соседние 28/29/30 = 96, т.е. код исполнялся; так же 60/70/90/124/138/163/176;
* закрывающие `}` и строки-литералы внутри таблиц/инициализаторов;
* логически недостижимые защитные ветки: `http_client_pool.cpp` 144-146
  («invalid connection in pool») — клиент валидируется на `release_connection`
  (160) и в очередь невалидным не попадает; `nats_client.cpp` 560-561
  («subscribe: connection is null») — между `ensure_connected()` и проверкой
  `m_conn` null-состояния достижимо только при гонке.

Реально достижимые непокрытые ветки — единицы, и они требуют live-брокера
(`l2_worker.cpp:493` «Skipping non-POST request», `l2_worker_nats.cpp:101`
«missing reply subject», DB-subscribe retry 302-305). Вынесены в план
следующего раунда; в этот раунд не брались, т.к. это асинхронные live-тесты с
риском флейка.

## 3. Переанкор `docs/coverage-baseline.json` (дрейф инструмента)

Per-file гейт упал на 6 файлах. Доказано, что причина — **смена инструмента
измерения**, а не код/тесты:

* с коммита baseline `daf5638` (round 105) изменены только `HISTORY.md`,
  doc-запись round 106 и line-endings вендоренного `match.inl` — **ни одна
  production-`.cpp`/`.hpp` не менялась** (`git diff --stat daf5638 HEAD`);
* `db_query_executor_oracle.cpp` — файл, который тесты не驱动 — тоже «потерял»
  строку (59→58): тестовая правка физически не могла на это повлиять;
* полностью чистый прогон с `CCACHE_DISABLE=1` (полный пересбор без ccache)
  воспроизвёл **точно те же** цифры (6448/7152, те же 6 файлов) → это не
  устаревший ccache и не флейк;
* дрейф детерминированный: два обычных прогона и один чистый дали идентичные
  результаты.

Механизм: базовый образ `ubuntu:26.04` — роллинг (и gcovr/gcc ставятся из apt,
не пинятся), между round 105 и 107 сменились инструментальные количества:
знаменатель строк 7146→7152 (config.cpp +2, http_client.cpp +4), а также заметно
сдвинулись счётчики ветвей (напр. `nats_client.cpp` ветви 760→794 при неизменных
строках 406/462, `l2_worker.cpp` 760→794, `dynamic_labeled_family.hpp` 146→164).
Затронуто 14 файлов, из них по строкам — 8 (6 «регрессий» по одному потерянному
покрытию + `l2_worker.cpp`/`proxy_init.cpp` по +2).

Действие (по решению пользователя): baseline **переанкорен** на честные текущие
чтения (`scripts/coverage-regression-check.py --update`), с этой записью.
Реальные пробелы не скрываются — потеряна ровно одна строка на файл, все они из
класса артефактов (см. 2а). Прецедент — round 88 («baseline обновлён — артефакт
смены знаменателя в logger.hpp»).

Итог: production 7152 строк, 6448 покрыты = **90.16%** (было 6447/7146 = 90.22%).
Рекомендация на будущее: запинить инструмент (digest базового образа и/или
версии gcc/gcovr), иначе дрейф будет повторяться и каждый раз требовать
переанкора.
